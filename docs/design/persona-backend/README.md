## 1. 一句话

**agents-io 是 agent 的路由层：所有渠道的消息由它收、盖章、按一张路由表分给后端，后端的回复由它投递。** 后端凭自己的钥匙接入，收到路由给它的消息，调接口把回复发回去。persona 的每个助手是一个后端，由一个薄扩展接入；同一个扩展把条目放进 persona 的收件箱。

## 2. 分工

| | 管什么 | 不管什么 |
|---|---|---|
| agents-io（一个常驻实例） | 渠道连接、来源盖章、路由表、持久队列、投递义务、因果可查、后端之间转信与防循环 | agent 怎么跑、界面、记忆、任务 |
| 后端（persona 的一个 manager、别的程序） | 收到消息后做什么、回什么 | 渠道的登录、重连、去重、限流、消息格式 |

这是 POSITIONING §3 的"只要通道"用法加宿主协议，不是新形态。后端用到的会话语义（一轮何时结束、过程卡片怎么更新）由后端自己负责，agents-io 只提供 `deliver` / `deliver.update` 这些原语。

## 3. 后端与钥匙

### 3.1 钥匙发给后端，不发给渠道

一个渠道的消息可以分给多个后端（同一个飞书群里，主人的话进主人的助手，家人的话进家庭助手），一个后端也可以收多个渠道。所以凭据的单位是后端：

```jsonc
"backends": {
  "persona-me":    { "note": "我的助手" },
  "persona-family": { "note": "家庭助手" }   // 回调地址（"callback": { "url", "timeoutMs" }）是 R4，还没有：现在写了加载时报未知键
}
```

已实现的配置还有两个键：`routes`（管理员登记的目的地）、`history`（能不能用 `history.read`，缺省关）。见 HOSTS §4.12。

- **能收到什么**：路由表里 `to: "<后端>"` 的规则命中的输入，别的看不到。
- **能往哪发**：它收到过的输入的回复路由，加上管理员为它预先登记的目的地（实现：按后端记的会话许可加 `backends.<id>.routes`，各算各的；不经过 `Policy.outbound`，也不经过宿主的 `outbound` 回调与出口检查，在 `policy.routes` 里放行或拒绝管不到后端的发送。INVARIANTS PB-2）。点击它自己发的卡片是它的输入，但不算“收到过的输入”来授予会话。
- **以谁的名义发**：路由规则给定的渠道账号。后端不能指定别的账号。

### 3.2 钥匙的生命周期

- 管理员新建后端时签发一把，**只显示一次**，服务端只存哈希。
- 遗忘或泄露：管理员**轮换**（签发新的，旧的立即作废，可选一个短的并存窗口）。不需要删渠道，路由规则和历史都不动。
- 删除后端：钥匙作废，指向它的规则挂起，队列里没确认的条目保留到管理员处理。

**实现与这一节的差别（2026-11-25）**：

- 没有并存窗口：轮换后旧钥匙立即作废，凭它在线的连接被关；新钥匙部署好之前这个后端不在线，条目留在队列里。
- “删除后端”就是从配置里删掉它（改配置要重启）。指向它的规则必须一起删掉或改指，否则配置加载失败，不是挂起；宿主推送并持久化的表里有这样的规则时，启动时整张宿主表被忽略。钥匙在下次启动时作废（要立即切断用 `aio backend revoke <id>`）。条目、游标、发送许可留在这个 id 下，同名加回来接着用；要清掉用 `aio backend forget <id>`。
- 管理凭据就是现有的宿主 token（`aio backend …`、`backends.*` 帧）加控制台会话（`/api/backends…`），没有另起一种。

**两级钥匙（2026-11-25，INVARIANTS PB-7）**。一个后端除了上面说的钥匙（读写钥匙，缺省）之外，可以另有一把**只读钥匙**：`aio backend key <id> --read`（帧与 HTTP 是 `access: "read"`）。每级至多一把，各自签发、轮换、作废，只影响本级的钥匙与连接；`forget` 关两级的连接、两把钥匙都留下；后端从配置里删掉，下次启动两把都删。

- 只读钥匙的连接是这个后端的旁观者：看得到路由给这个后端的条目（`inbound.read`）和它读得到的媒体（`blob.stat` / `blob.get`），放开 `history` 时能 `history.read`；确认、发送、改消息、标记、上传一律 `forbidden`，文字固定（`this key is read-only`）。hello 的应答用 `backend.access` 说明级别，`features` 只列用得了的。
- 旁观只有拉取，没有推送。只读连接的 `inbound.read` 不登记消费者、不写任何行：游标只由读写连接的确认前移，所以至少一次的投递不受它影响；清理只看消费者，所以旁观者不会拖住条目，也因此没有投递保证（后端确认过、过了保留期的条目它看不到）。只读连接不进“每个后端一条推送连接”那个位置，可以有多条，顶不掉读写连接。有界：每个在等的长轮询在每次入队时（条目给谁的都算）被唤醒、重读一次队列，不设上限的话一把只读钥匙可以让每次入队任意地慢，拖住读写连接的推送；所以一条只读连接至多 4 个在等的长轮询、一个后端至多 32 条说过 hello 的只读连接，超出的答 `busy`（读写钥匙与宿主 token 的连接不变）。为什么不给旁观者推送副本：要按连接记位置、处置慢的旁观者，而且推送的 `accepted` 对它没有意义；长轮询在入队时就被唤醒，延迟相同。
- 只读钥匙前缀 `aiobr_`（读写是 `aiob_`），只为肉眼分得出；级别以存下的为准。它存在另一张表（`daemon_backend_access_keys`），原来的 `daemon_backend_keys` 一字不改：原表一个后端只有一行，给它加级别要重建表，重建之后旧版本的守护进程打不开库；让旧版本还能打开的同表做法，旧版本又会把只读那一行当成完整的钥匙。分开存，升级不用迁移（原有的钥匙就是读写钥匙），回退时读写钥匙照常、只读钥匙不被认识。代价：旧版本也不删它，回退期间从配置里删掉的后端，同名加回来、再升级之后旧的只读钥匙又能用；回退前先 `aio backend revoke <id> --read`。
- 没有 `backends.access` 这个 feature 的守护进程会忽略 `access`、照样动读写钥匙：命令行在发帧前检查，别的调用方核对应答里的 `access`。
- 没做的：给旁观者的推送、旁观者自己的持久游标、同一级多把带名字的钥匙、`history` 按级别的开关、按旁观方分开的限额（32 条只读连接是这个后端的各方共用的）、`/ws` 上还没 hello 的连接的数量上限。

### 3.3 两种凭据分开

| 凭据 | 谁拿 | 能做什么 |
|---|---|---|
| 管理凭据 | 主人（控制台登录） | 渠道、路由表、后端的增删改、轮换钥匙、`explain` |
| 只读钥匙 | 这个后端的旁观者 | 看这个后端的队列条目（不消费、不移动游标）、读它读得到的媒体、放开时读历史；什么都改不了（PB-7） |
| 后端钥匙（读写） | 一个后端 | 收自己的输入、确认、`deliver`、`deliver.update`、`message.ack`、`blob.stat` / `blob.get` / `blob.put`（只读得到路由给它的条目里的媒体和它自己上传的字节；上传进它自己的暂存区，24 小时过期，有配额；附件只能是这两类引用。HOSTS §4.13，PB-6）、`history.read`（限自己的条目；要管理员按后端放开 `backends.<id>.history`，缺省关。放开后读得到同一会话里更早的全部消息，包括路由给别的后端或本地 agent 的）、改自己的回调地址（R4，未做） |

后端钥匙改不了路由表。否则任何一个后端都能把别人的消息改道给自己。

### 3.4 怎么收

持久队列不变（HOSTS §2.1：至少一次，确认后才前移，后端不在线只会变慢）。每个后端有自己的游标，只看到路由给它的条目。三种取法，语义相同：

| 方式 | 适合 |
|---|---|
| 长连接（`/ws`，带钥匙） | 没有固定地址的后端：各台机器上的 persona 扩展 |
| 拉取（`inbound.read`） | 一次性脚本、定时任务 |
| 回调（agents-io POST 到后端登记的地址） | 有固定地址的服务 |

回调的要求：请求带时间戳和用钥匙派生的签名（防伪造与重放）；后端答 2xx 才算确认；失败按退避重试，不丢；幂等键是条目 id。

### 3.5 部署

- 一个实例跑在家里的集群上，**只在内网与 tailnet 可达**：它经手所有人的消息。
- 状态（路由表、队列、outbox、blob）要落盘到持久卷。
- 渠道里需要本机会话的（open-lark 是一个独立的常驻服务，走 HTTP）不受影响；飞书机器人、邮件本来就是出站连接。

### 3.6 后端自己发的消息回来（2026-11-25，已实现；INVARIANTS PB-8，HOSTS §4.12）

有的通道把账号自己发出的消息也当入站消息交上来（个人账号类的通道会，机器人通常不会）。本地 agent 的 turn 发的消息，守护进程靠出站索引认得（ID-8）；后端的 `deliver` 没有 turn，不在那个索引里，它的回声原先按那个账号发的普通消息路由：进发它的后端的队列（后端回自己的话，成环），或者命中 `dispatch` 规则开一轮。扩展一侧有过补救（按消息 id 与文字认），有说明在案的缺口。

决定：

1. **按出站记录的消息 id 认，不看文字。** 每次后端投递的平台消息 id（拆开的每一条）本来就记着、不过期（点击归属与编辑权靠它，PB-1、PB-2）。入站信封的 id 或它修订的那条消息的 id 命中，就是回声。别人发的同样文字的消息永远不会被吞。
2. **回声是本部署自己的，不是谁在说话。** 盖章与 `policy.selfAccounts` 认出的回流相同（`self`、没有主体），之后照现有的回流规则走：规则要写 `includeSelf` 才命中，`dispatch` 降为 `context`。没有另造一套语义。
3. **发它的后端收不到，规则怎么写都一样。** 带 `to` 指向它的规则跳过，`explain` 里记 `own_echo`。这是在回流规则之上多出来的唯一一条：`includeSelf` 的意思是“我要看这个账号说了什么”，不是“把我自己说的话再给我一遍”。
4. **别的后端缺省看不到，写了 `includeSelf` 才看到，收到的是标了 `self` 的条目。** §3.1 的例子里两个助手共用一个群：如果缺省就把甲发的话当普通消息给乙，乙会回，乙的话又给甲，两个后端来回成环，谁都没写错规则。所以缺省不给；要旁观的一方显式要，拿到的条目带着“这是本部署的账号发的”，由它自己决定用不用，不能把它当成有人对它说话。这与现有回流对“要它的规则”的处理一致（本地 agent 的规则写了 `includeSelf` 也只记作上下文）。
5. **回声比投递记录先到时：短等，再只对正在发送的后端留住。** 通道可以在发送调用返回之前就交上回声。后端的发送进行期间，同一通道、同一会话 id 的入站先短等它结算再认：一次投递合计至多 2 秒（`backendEchoWaitMs`），只在等了能认出来的地方等（证据够、不是点击、不是已认得的自己的消息），等的是那个会话的入站，不是整个通道。发送比这更久（拆成多条、带附件、在重试）时，这条入站对别的规则按普通消息放行，给正在发送的那个后端的队列条目搁置到它的发送结算：是它自己的回声就丢弃，不是就入队。评审里比较过两个方向：一直等到结算（别人的消息在慢发送、重试期间一直被拖住，不回声的通道也一样），和到期限全部放行（发它的后端收到自己的话，回得慢的后端每次都漏，成环）。取的是中间：对“发它的后端不收到自己的话”不放行，代价只落在正在发送的那个后端身上（别人的消息对它晚到，不丢）；对别的消费者到期限放行，代价是晚到的回声在它们那里是一条普通消息。让适配器在平台返回 id 的那一刻就报上来（`send` 返回之前）可以把后一个缺口也关掉，要动通道接口，没有做。turn 的发送（ID-8）原先就没有这个等待，这次没有动它。

没做的：结果不明的投递（没有消息 id）的回声认不出，路由层不按文字猜（那是猜，错了就吞掉别人的话；扩展可以自己猜，它知道自己发了什么）；宿主 token 的 `deliver` 的回声不认；没有给后端的 hello 加 feature 表示这一条（行为对后端是“少收到一类条目”，不需要它配合）。

## 4. agents-io 要补的

| # | 内容 | 现状 |
|---|---|---|
| R1 | 多后端：多个带角色的连接同时在线，各凭钥匙识别 | 已实现：凭钥匙 `host.hello` 的连接是 `backend:<id>`，不占宿主位，每个后端一条推送连接；凭宿主 token 的宿主仍至多一个（HOSTS §4.12，PB-1） |
| R2 | 队列按后端过滤：路由规则 `on: "host"` 加 `to: "<后端>"`，每个后端一条游标 | 已实现：条目与消费者带后端，消费者 `backend:<id>` 只走自己的条目；一条输入给两个后端是两条（HOSTS §2.1，PB-1） |
| R3 | 后端钥匙：签发、哈希存储、轮换、作废；与管理凭据分开 | 已实现：`aio backend key / rotate / revoke / forget`、`/api/backends…`，只存 SHA-256，只显示一次；没有并存窗口；钥匙只能开 `/ws`、只能用白名单里的帧（PB-3）。钥匙分读写与只读两级（`--read` / `access: "read"`），只读的只能旁观（PB-7） |
| R4 | 回调推送与签名 | 未做 |
| R5 | `deliver` 与出口检查按后端算范围 | 已实现：会话许可（收到过输入的会话，加登记的目的地）、回复目标与被标记、被改的消息都检查，不满足答 `route_not_allowed`；operationId 按后端分开（PB-2）。宿主的 `outbound` 回调与出口检查不看后端的发送 |
| R6 | 后端之间转信：一个后端发给另一个后端的地址 | 未做。agent 之间的寻址、因果链、跳数上限已有（决定 13），要让"后端"成为一种地址 |
| R7 | 媒体：远程后端取条目里的图片、文件、语音的字节，上传自己的附件 | 已实现：宿主协议的三个帧 `blob.stat` / `blob.get` / `blob.put`（feature `blobs`），每帧至多 1 MiB，按范围读、分片传，本地 socket 与 `/ws` 相同；没有加 HTTP 端点（钥匙在 `/api/*` 上一律 403 不变）。后端只读得到路由给它的条目里的媒体（记 30 天）和它自己的上传（暂存区按后端分开，24 小时过期，每个后端合计至多 `blobs.maxBytes` 的 8 倍、256 个）；`deliver` / `deliver.update` 的附件只能是这两类引用，否则 `unknown_blob`（原来是“知道引用就发得出”），一条消息至多 32 个（`too_many_attachments`）。一个后端能让守护进程占的内存与做的事有界：没传完的上传按 64 KiB 一块存，同一个上传只复制进共用库一次、一次一个，`blob.get` 的应答一个写出才读下一个（`/ws` 上也是）；它给的 mime 与名字在共用库里是临时的。宿主 token 用同样的帧读写共用的 blob 库（HOSTS §4.13，PB-6） |
| R8 | 规则标签：管理员在规则上写的不透明 `tag`，告诉后端这条条目怎么处理 | 已实现：`Binding.tag`（在 `on: "host"` 或带 `callout` 的规则上是标签：1 到 128 个字符、无控制字符，不合的整张表答 `invalid`；别的规则上的 `tag` 键照旧忽略，原来自己带着这个键的表不受影响）原样抄到条目的 `InboundItem.tag`，`explain` 里这两种规则的命中带它；内核不解读（HOSTS §2、§2.1，RT-1、EX-1） |

R1–R3 是第一条链路的前提。

## 5. persona 扩展 `agents-io`

Go 写的一个 persona 扩展，在本仓库的 `persona-plugin/`（自成一个 Go 模块，不在 pnpm 工作区里；做了哪些、没做哪些见它的 README）。**每个 manager 装一份，每份配一把后端钥匙。** 通用于所有渠道。它用 persona 发给扩展的受限令牌（`pext_`，范围 `assistant.ask`、`agents.read`、`agents.control`，可选 `agents.permission_mode`）调 hub，只能碰自己那个 manager。

### 5.1 收到一条输入

1. 从 agents-io 的长连接收到条目（来源、渠道会话、内容、回复路由、路由规则给的标签：条目的 `tag`，即 `InboundItem.tag`，规则上写什么就是什么，R8）。内容里的图片、文件、语音是 blob 引用：要字节时用 `blob.get` 按范围取（每片至多 1 MiB），取完自己核对 SHA-256 等于引用（R7；记 30 天，收件箱里要留的在收到时就取）。
2. 按标签选目标：

| 标签 | 做法 |
|---|---|
| `inbox` | 不唤醒助手，只进收件箱（§5.4） |
| `chat` | 这个渠道会话对应的助手对话；没有就开一个（`POST /api/v1/assistant/conversations`，带 `X-Persona-Op-Id`），有就发进去（`POST /sessions/{mid}/{sid}/messages`，`client_msg_id` 用条目 id） |
| `guest` | 同上，但开的是访客对话（`guest: { tools }`：只有列出的连接器工具，没有记忆和主人的设置） |
| `agent` | 发给规则指定的 coding agent 会话，停了就 `resume_session_id` 续上 |

3. 文字前面带一行来源（谁、哪个渠道、`ref=`）。persona 的消息没有"发送者"字段，带权限的调用一律算主人说的，所以"这是别人说的"只能写在文字里，并靠 §6 的隔离兜住。
4. 给 agents-io 确认这条。结果不明时不重发，按 `unknown` 处理（persona 自己的规则也是这样）。

渠道会话 ↔ persona 对话的对应表存在扩展自己的存储里。

### 5.2 回答回到渠道

persona 没有"这条消息的回答是什么"的接口。它自己的通道管线这样判，扩展照做：

1. 在 items 里找到带自己 `client_msg_id` 的那条；
2. 会话在跑、或在等回答时一直等（`agent.finished` 事件是提示，不是依据）；
3. 取它之后的助手文字，最后一段是 final。

读法：`GET /sessions/{mid}/{sid}/items?after_seq=N` 轮询（扩展令牌连不了 WS）。

- 过程：先 `message.ack { state: "working" }`；要过程卡片就 `deliver` 一张再 `deliver.update`，收尾 `final: true`。
- final：`deliver`，`operationId` 由条目 id 派生，重复不会发两次。
- 人在 persona 的 app 里对同一个对话说的话，不是这条输入引起的，不往渠道投。

### 5.3 审批与提问

- 发现：`agent.needs_you` 事件，或轮询 `GET /interactions`。
- 发到渠道：`deliver` 一张带按钮的卡片（`actionPrefix` 让点击回到这个后端）。已实现的规则更严：点击只回到发卡片的那个后端（仍要有一条 `to` 是它的规则命中），别的后端、宿主和内核的按钮解析都拿不到；带 `to` 的规则也只接它那个后端发的卡片上的点击（PB-1）。
- 有人点了：agents-io 把点击作为一条输入送回来，带点击者的盖章身份；扩展确认是主人后调 `POST /interactions/{id}/resolve` 或 `/choose`。
- 在 persona 里先答了：下次读到它不在挂起列表里，`deliver.update` 把卡片改成"已在别处回答"。
- persona 拒绝外部回答的两种（交出密钥、澄清）：卡片只显示、不给按钮。

### 5.4 收件箱连接器

- `inbox.collect` → 把标签 `inbox` 的条目（可选：也包括被 `chat` 处理的条目的镜像）转成 `InboxThing`：`thread` 用渠道会话引用（去重键），`sender`、`preview`、`at`、`url`，平台原始数据放 `extra`。
- 有新条目时发 `changed { scope: "inbox" }`。
- 分级：声明 `fallback` 能力并给 `extra.rule_tier`，由路由规则的标签来，不需要 persona 再调模型分拣。
- `inbox.reply { thread, text, client_id }` → agents-io `deliver`，`operationId = client_id`。
- `inbox.settle` → `message.ack { state: "done" }`。
- 条目详情（`inbox_item` 界面槽）按 `extra` 画，飞书卡片仍然像卡片。

### 5.5 给助手的发消息工具

助手要主动往某个渠道、某个人、或另一个助手发消息时调它（`mcp_servers` 或 skill），扩展转成 agents-io 的 `deliver` 或后端之间的转信（R6）。助手之间：`Policy.contact` 缺省拒绝，配置里放行这一对；跳数与成对上限防循环；`aio explain --chain` 能查。

文字版已在 `persona-plugin` 0.2.0 实现：连接器的写操作 `agentsio_send`（每条都要主人在手机上确认）加只读的 `agentsio_destinations`，经 agents-io 的 `deliver` 发出，见它的 README。后端之间的转信（R6）未做。

## 6. 谁的话进谁的助手

persona 不区分调用者是替谁说话。隔离由路由表选后端和标签来实现：

| 来源 | 路由到 | 依据 |
|---|---|---|
| 主人 | 自己的后端，`chat` | 就是本人 |
| 家人等认识的人 | 专给他们用的后端（家庭助手），`chat` | 那个 manager 名下只有给她的机器、凭据和记忆；隔离单位是 manager |
| 其他人、群里的陌生人 | `guest`，或只进 `inbox` | persona 为非主人设计的模式 |

## 7. 渠道归属与 `openlark` 扩展的 PR

**一个渠道账号只有一个接入方在收。** 现在飞书个人账号两边都订阅了 open-lark 的事件流，同一条消息各处理一次；persona 那边若开着 `/agent` 或自动代答，会双重回复。

`openlark` 扩展在它自己的扩展仓库里。给它提一个 PR，加一个**可选开关，缺省不变**：

- 配置项 `messaging`（缺省 `true`，现有用户零变化）。`false` 时：
  - 不连事件流，不跑收件箱、release、`/agent` 与自动代答循环；
  - 连接器只留 `status` 和只读工具（`lark_chats`、`lark_messages`、`lark_search`），不再列出 `lark_agent_reply`；
  - `api/lark` 里发送、回复、加密发送的路由答 404，Base 与文档评论照常（`worklog`、`agent-board` 依赖它们）；
  - `gate.json` 里发消息、转发、撤回的写规则改为拒绝，助手说明换成"发消息走另一个工具"；
  - "消息"页、收件箱事件详情、显示设置三项贡献不生效。
- 不改的：skill、`ol` 闸门、授权中转、MCP 工具、个人 agent 来源、多账号。
- 顺带可做：让扩展读 `initialize` 里的 `active`（现在只定义了字段没读），关掉单项贡献时对应的后台循环也停。

知识库归档现在靠扩展自己收到的消息；`messaging: false` 下它是否保留一条只归档的订阅，见 §10 第 4 项。

## 8. 不变量增补（草案）

- **PB-1** 一个后端只收到路由给它的输入；它的钥匙读不到别的后端的条目，也改不了路由表。（已进 INVARIANTS，有测试）
- **PB-2** 一个后端只能往它收到过的输入的回复路由和管理员为它登记的目的地发。（已进 INVARIANTS，有测试）
- **PB-3** 后端钥匙只存哈希；轮换后旧钥匙立即不能用（或在声明的窗口结束时）。（已进 INVARIANTS，有测试；没有窗口，立即作废）
- **PB-4** 回调未被确认的条目不丢、不跳过；同一条目重复推送时幂等键相同。（未做，随 R4）
- **PB-5** 一个渠道账号同一时刻只有一个接入方在收。（未做：属于 openlark 扩展一侧）
- **PB-6** 后端只读得到路由给它的条目里的媒体和它自己上传的字节；上传按后端隔离、有上限、过期删除；附件只能是这两类引用。（已进 INVARIANTS，有测试。编号跳过 PB-4、PB-5，它们留给上面两条）
- **PB-7** 只读钥匙是这个后端的旁观者：看得到给它的条目与媒体，不消费、不移动游标，什么都改不了；两级钥匙各自轮换、作废。（已进 INVARIANTS，有测试）

## 9. 没有核实的

- 扩展令牌下 `guest` 的可用性与 `GET /assistant/capabilities` 的探测结果；用 `/sessions/…/messages` 往助手对话发消息所需的范围。
- persona 的 A2A 端点（`/api/v1/a2a/{machine}/{session}`，任务形状的结果）对助手对话是否可用。可用的话 §5.2 不用自己判一轮的边界。它最近两周改动很多。
- 文件发送接口（没读）。agents-io 一侧收发媒体的帧已经有了（R7），persona 一侧怎样把助手产出的文件交给扩展、扩展怎样把取到的图片交给助手对话，都没读、没试；扩展（Go）要自己做分片上传、按范围读和 SHA-256 核对，发附件时总是带 `name`。真实链路（飞书图片进后端、后端发图回群）没有验证。
- `openlark` 扩展本地检出停在 2026-11-08，上游现状没看；`git fetch` 当时没连上。open-lark 新版把 `/agent/v1` 标为旧接口且默认关闭，扩展是否已迁移没核实。
- persona 的接口这两周变动密集。扩展要做版本探测，变了明确报错。

## 10. 待拍板

1. **钥匙发给后端、管理凭据与后端钥匙分开、遗忘则轮换**（§3）。这是对 owner 原话"一个渠道一个 ak、带 ak 才能修改、遗忘只能删渠道"的三处调整。
2. **家人的消息进家庭助手的普通对话，陌生人进访客对话或只进收件箱**（§6）。
3. **只有主人能在渠道上回答审批**（§5.3）。
4. **知识库归档**：`messaging: false` 时先保留一条只归档、不进收件箱、不回复的订阅（PB-5 对它开一个只读的例外），量一下再决定是否由 agents-io 供给。
5. **第一条链路**：家庭飞书群 → 家庭助手（persona 的一个 manager）→ 回到群里。

## 11. 分步

| 步 | 内容 | 验收 |
|---|---|---|
| P0 | 在 persona 里建家庭助手 manager，把她的机器移过去，搬规则与 skill | 在 persona app 里能和她对话 |
| P1 | agents-io：R1–R3（多后端、按后端过滤、钥匙）；集群部署 | 两个后端各拿各的条目；钥匙轮换后旧的被拒 |
| P2 | 扩展最小：`chat` 标签、发送、判一轮、final 回到渠道 | 群里 @ 她，回答回到群里；`aio explain` 能从回答查到那条消息 |
| P3 | 过程卡片、审批（含撤卡）、访客对话 | 审批在飞书上点了生效；在 persona 里答了，飞书卡片改掉 |
| P4 | 收件箱连接器、条目详情、回复 | 条目出现在家庭助手的收件箱；在收件箱里回复，对方收到一次 |
| P5 | `openlark` 的 PR 合并并发版；逐个渠道切归属 | 同一条消息只被处理一次 |
| P6 | 回调推送（R4）；发消息工具与后端之间转信（R6） | 你的助手让家庭助手办一件事，结果回到你的对话；来回超过上限会停 |
